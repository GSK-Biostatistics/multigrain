# Fast Shortcut: What Changed and How to Compare It with v1.0.0

*Branch `fast-shortcut`, based on `7884824` (v1.0.0). Implements `debug/improve-shortcut.md` (git-ignored). Written 16 October 2026. The kernel and its tests are in commit `0344474` (built with κ = 1). The calibrated κ = 2, the switch-rule test, DESCRIPTION, NEWS and this file are in `abcf908`, the build to benchmark. The scripts and results in `dev/review/shortcut_table/` are not yet committed.*

**Build label.** `Version: 1.0.0.9000`, plus a DESCRIPTION field `Config/multigrain/build: 1.0.0-fast-shortcut`. R does not accept `1.0.0-fast-shortcut` as a version string, so the label lives in its own field. Read it with `packageDescription("multigrain")[["Config/multigrain/build"]]`. On v1.0.0 the field is `NULL`.

---

## In Brief

* `graph_shortcut()` and `graph_shortcut_parallel()` now contain two kernels:
  * the original **sequential** kernel, kept verbatim, which updates the graph after every rejection;
  * a new **table** kernel, which computes the critical value of every hypothesis in every intersection once per call and then only looks them up in each simulated trial.
* The exported signatures, return types and every R call site are unchanged. The kernel is chosen inside C++ at each call.
* **Results are identical.** No rejection indicator differed between the two kernels in 2.0e9 indicators checked locally. v1.0.0 and this build produced identical rejection matrices in every benchmark cell.
* **Speed (local, serial).** See [Local Results](#local-results). For m ≤ 14 the table kernel ran 1.2–6.7× faster than v1.0.0 per call: 1.5–6.7× at high power and 1.2–3.3× at low power. One objective evaluation in the GA phase (m = 5–10, N = 5e4) ran 2.2–4.7× faster, because the kernel is about 90% of each evaluation.
* **Not yet measured:** the curated problems, full optimisation runs, the HPC nodes, and more than 12 threads.

### How the Table Kernel Works

The local weight of a hypothesis depends only on which hypotheses are still unrejected (Bretz et al. 2009), not on the order in which the others were removed. So for one candidate graph:

1. **Build the table once per call.** For every non-empty subset S of hypotheses, store the critical value `c_j(S) = alpha * w_j(S)` of each hypothesis.
   * Rows are indexed by the bitmask of S (bit `j-1` is `H_j`). There are 2^m rows of m doubles: 16 KB at m = 8, 1.75 MB at m = 14, 160 MB at m = 20.
   * The build is depth-first over subsets, removing hypotheses in increasing index order, and costs O(2^m m^2).
   * It runs in alpha-space with exactly the sequential kernel's arithmetic: levels start at `w[i] * alpha` and update as `a_i + a_k * g_ki`, with the same graph update and the same rule for a degenerate denominator.
   * Because of this, any set reached by rejecting hypotheses in increasing index order gets critical values bit-identical to the sequential kernel's. This is a deliberate change from the design's prototype, which multiplied by alpha at the end.
2. **Walk the table per trial.** Start from the full set. Reject every hypothesis in S whose p-value is strictly below its critical value, remove them all at once, and repeat until nothing is rejected.
   * Each step is O(m), and there is no per-trial copy of the graph.
   * Rejecting several hypotheses in one step reaches the same final set, because local weights only grow as S shrinks.
   * Only members of S are tested, with strict `<`. So a hypothesis with p = 0 and weight 0 is never rejected and cannot stall the loop (graphicalMCP issue #47).

### Kernel Selection

* **Rule (`"auto"`, the default).** Use the table kernel when `m <= table_max_m` and `2^m <= TABLE_KAPPA * N`, where N is the number of trials. `TABLE_KAPPA` = **2**, calibrated locally, so the rule is the table kernel when 2^(m−1) ≤ N. Otherwise use the sequential kernel.
  * The table build costs about 2^m m^2 once, and the sequential kernel about N m^2 (1 + rejections per trial). The rule sends large m with small N to the sequential kernel.
  * In the GA phase (N = 5e4) the table kernel is used up to m = 16. In a local phase with N = 1e6 it is used up to m = 20.
* **Hard cap.** The table kernel never runs with m > 20, the 160 MB table. Forcing it above that is an error.
* **Thread count is ignored on purpose.** Kernel choice, and therefore output, never depends on `num_threads`, so results do not change with thread count. The build is serial, so with many threads the true break-even point is somewhat lower than the rule assumes (see the report, B4).
* **Internal options.** These are undocumented and read once per call on the main thread:
  * `options(multigrain.shortcut_kernel = "auto" | "sequential" | "table")` forces a kernel. An invalid value is an error.
  * `options(multigrain.shortcut_table_max_m = 0..20)` caps the table kernel under `"auto"`; the default is 20 and 0 forces sequential.

### Parallel Version

* `graph_shortcut_parallel()` builds the table once on the main thread before `parallelFor`.
* `TableShortcutWorker` walks it read-only through raw pointers; each thread needs only O(m) scratch.
* Serial and parallel use the same walk function, so their output is identical by construction.
* Table-kernel grain size: same heuristic as before, with m^2 operations per trial and a target of 1e5 per chunk. Grains from 64 to 10,000 all landed within measurement noise, so nothing was tuned further.

### Internal Helpers (`@noRd`, for tests and dev scripts)

* `multigrain:::graph_shortcut_kernel(n_trials, m)` returns `"table"` or `"sequential"`: the choice `"auto"` would make under the current options.
* `multigrain:::graph_shortcut_table(alpha, w, G)` returns the raw 2^m × m critical-value table, where row `mask + 1` is the set with that bitmask.

### Local Results

Full tables, conditions and caveats are in `dev/review/shortcut_table_report.md`. These are local hypotheses for the HPC run to confirm: a Windows laptop with 10 physical cores, serial unless stated, timed on AC power. Two earlier passes were spoiled by standby and battery power and were discarded. A full repeat on the committed build `abcf908` reproduced every conclusion, with speedups within a few per cent (median −1.8%). Read single figures as ±10%.

* **Identity.**
  * 0 differences between the kernels in 2.0e9 indicators (m = 2–16, dense and sparse graphs, three power levels).
  * v1.0.0 equals this build in every benchmark cell, and objective values are identical.
* **Per call, table kernel vs v1.0.0, N = 5e4:**

  | m | high power | low power |
  |---:|---:|---:|
  | 5 | 3.61 → 1.64 ms (2.2×) | 2.12 → 1.27 ms (1.7×) |
  | 8 | 9.92 → 2.88 ms (3.4×) | 4.34 → 2.22 ms (2.0×) |
  | 10 | 15.9 → 3.8 ms (4.2×) | 5.76 → 2.71 ms (2.1×) |
  | 12 | 25.0 → 4.8 ms (5.2×) | 8.59 → 3.34 ms (2.6×) |
  | 14 | 38.7 → 6.9 ms (5.6×) | 13.0 → 5.2 ms (2.5×) |

  At N = 1e6 the gains are similar or larger: 3.4× at m = 8 and 6.6× at m = 16, high power.
* **One GA objective evaluation** (`create_obj_func()`, N = 5e4): m = 5 3.7 → 1.7 ms; m = 6 5.3 → 2.1 ms; m = 8 10.0 → 2.8 ms; m = 10 16.8 → 3.6 ms.
* **Threads.** At equal thread counts (1–12) the table kernel stays 2.5–8.9× faster for m = 8–16. The exception is m = 16 with N = 5e4 on many threads (1.1× at 12 threads), where the serial table build dominates.
* **Switch rule.** `"auto"` was never slower than the original kernel. The cost of a rule that ignores power: in high-power cells just past the boundary (2^m/N ≈ 2.6, e.g. m = 17 at N = 5e4), the table would have been 2.2–2.5× faster than what `"auto"` picks.

## (b) Comparing with v1.0.0: High-Level Instructions

The benchmarking agent knows the problems, seeds and cost conventions. This only fixes the shape of the comparison.

1. **Two builds, two libraries.**
   * Install v1.0.0 (`7884824`) and this branch (`abcf908` or later; record the SHA used) into separate R libraries.
   * Load each in its own R process with `library(multigrain, lib.loc = ...)`.
   * Confirm which build is loaded via `packageVersion()` (`1.0.0` vs `1.0.0.9000`) or the `Config/multigrain/build` field, and record it with every result.
   * Build both with the same compiler and flags.
2. **Identity first.**
   * For each problem and seed, with the same `num_threads` and node type, check that the GA trace, the delivered graph and the holdout score are `identical()` between builds.
   * A second, cleaner A/B needs only one build: run this build with `options(multigrain.shortcut_kernel = "sequential")` and again with the default `"auto"`. This isolates the kernel from every other difference.
3. **Then speed, at equal parallelism.**
   * Compare per-generation time and total run time only between runs with the same `num_threads` on the same node type.
   * Report the pruning and local phases separately. They use larger N, so the gain there should be larger.
4. **What to expect, as hypotheses to confirm:**
   * the kernel is most of each GA evaluation, so per-generation speedups of roughly 2–4× for m = 5–10, larger at higher power (more rejections per trial);
   * no slowdown anywhere, since `"auto"` falls back to the original kernel where the table would not pay.
5. **If a run is not identical.** Check the build flags first. Builds that enable FMA contraction (for example `-march=native`) can change the last bits of the two kernels' arithmetic differently. A genuine difference needs a p-value within about 1e-12 (relative) of a critical value. `dev/review/shortcut_table/common.R::replay_trial()` replays a single trial through both kernels to classify it.
